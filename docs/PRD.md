## 1. Назначение

GitHubBackup — приложение для Windows 11, которое делает локальные резервные копии и архивы GitHub-репозиториев:

- клонирует репозитории (со всеми ветками, тегами, сабмодулями, LFS-файлами и wiki) на локальный диск и поддерживает клоны в актуальном состоянии;
- при изменениях на сервере создаёт ZIP-архив клона вместе с папкой `.git`. Каждый архив сохраняется рядом с предыдущими, получается история снимков;
- находит новые, пропавшие и переименованные репозитории в отслеживаемых аккаунтах и сообщает о них;
- ведёт историю запусков и архивов, её можно смотреть в UI.

Приложение запускается вручную (UI или консоль), а позже — по расписанию через Планировщик заданий Windows в тихом режиме.

## 2. Область охвата

### 2.1. Входит

- Бэкап репозиториев с **github.com** (включая организации на тарифе GitHub Enterprise Cloud, которые работают на том же github.com).
- Аккаунты двух типов: пользователи и организации.
- Отдельные репозитории, указанные по URL (в том числе чужие).
- Исключения по маскам.
- Обнаружение новых, пропавших и переименованных репозиториев.
- Клон: все ветки и теги, сабмодули, LFS для выбранной ветки, wiki отдельным архивом.
- ZIP-архивация через 7-Zip.
- Файл состояния в папке каждого репозитория.
- История запусков в SQLite.
- Консольное приложение: интерактивный режим, тихий режим (`--silent`), проверочный прогон (`--dry-run`), фильтры по аккаунту или репозиторию.
- Приложение с UI на WPF.
- Логирование в текстовые и структурированные файлы с разбиением по датам, опциональный экспорт OpenTelemetry.

### 2.2. Не входит (сейчас)

| Что | Комментарий |
|---|---|
| Очистка старых архивов и истории | Добавим позже отдельной функцией |
| Восстановление из архива | Архив — обычный ZIP с рабочим клоном, восстановление ручное |
| Бэкап Issues, Pull Requests, Releases, Actions, Projects | Только git-данные и wiki |
| GitHub Enterprise Server (собственный сервер компании) | Адрес API вынесен в настройки на будущее, но поддержка не реализуется и не тестируется |
| Параллельная обработка репозиториев | Строго по одному |
| Кроссплатформенность | Только Windows |
| Автоматическая регистрация задачи в Планировщике | Решим в фазе 5 (см. раздел 13) |

## 3. Термины

| Термин | Значение |
|---|---|
| Аккаунт | Пользователь или организация GitHub, задаётся URL: `https://github.com/AMTOSS` |
| Owner | Логин владельца репозитория (пользователь или организация) |
| Отслеживаемый репозиторий | Репозиторий, записанный в `backup-config.json`, в группе аккаунта или в группе отдельных репозиториев |
| Корень бэкапов | Общий каталог по умолчанию для архивов всех репозиториев (`backupRoot`). Может находиться под облачной синхронизацией (OneDrive и т. п.) |
| Папка архивов репозитория | Каталог, где лежат архивы и файл состояния репозитория (внутри корня бэкапов или по своему пути) |
| Корень клонов | Каталог для рабочих клонов (`sourcesRoot`), по умолчанию `sources\` рядом с exe. Хранится **отдельно** от архивов, чтобы тысячи файлов клонов не попадали в облачную синхронизацию |
| Клон | Рабочая копия git `<sourcesRoot>\<owner>\<repo>`, только для чтения |
| Снимок ссылок (ref snapshot) | Набор пар «имя ветки или тега → SHA» на сервере на момент архивации |
| Файл состояния | `.backup-state.json` в папке архивов репозитория |
| Запуск (run) | Один вызов процедуры бэкапа из UI или CLI |

## 5. Пользовательские сценарии

1. **Первый запуск.** Пользователь указывает корень бэкапов и аккаунты, задаёт токен. Программа находит все репозитории аккаунтов, показывает их как новые. Пользователь подтверждает (при необходимости правит ветку, путь, добавляет в исключения), программа клонирует и архивирует.
2. **Обычный ручной запуск.** Программа проверяет каждый репозиторий. Где были изменения, обновляет клон и создаёт новый архив, где изменений нет, пропускает. В конце показывает сводку.
3. **Появился новый репозиторий.** Программа сообщает о нём и предлагает данные для записи в настройки. После подтверждения или правки записывает их и делает бэкап.
4. **Репозиторий удалили или отозвали доступ.** Программа сообщает об этом, помечает репозиторий как недоступный, ничего не удаляет.
5. **Репозиторий переименовали.** Программа распознаёт переименование и предлагает переименовать папку или продолжить работу в старой.
6. **Запуск по расписанию.** `GitHubBackup.Cli.exe backup --silent` работает без вопросов, решения принимаются автоматически, итог отражается в коде возврата, логе и истории.
7. **Разбор сбоя.** Один репозиторий упал с ошибкой. Пользователь смотрит сводку и лог, затем перезапускает бэкап только для него: `--repo owner/name`.
8. **Просмотр истории.** В UI пользователь смотрит прошлые запуски и все архивы конкретного репозитория.

## 6. Функциональные требования

### 6.1. Источники репозиториев

- **FR-1.1.** В настройках задаётся список **аккаунтов** по URL (`https://github.com/<login>`). Тип аккаунта (пользователь или организация) определяется автоматически через API (`GET /users/{login}`, поле `type`).
- **FR-1.2.** У каждого аккаунта есть **список его репозиториев**. В список попадают репозитории, подтверждённые пользователем (см. 6.2). Для каждого репозитория можно задать:
  - ветку для checkout (`branch`), по умолчанию — ветка по умолчанию на GitHub;
  - свою папку (`path`).
- **FR-1.3.** Для аккаунта можно задать свою папку (`path`) и список исключений (`exclude`).
- **FR-1.4.** Отдельная группа **отдельных репозиториев** задаётся по URL (`https://github.com/<owner>/<repo>`), с теми же необязательными `branch` и `path`.
- **FR-1.5.** Бэкапятся все типы репозиториев: публичные, приватные, форки, архивные (archived).
- **FR-1.6.** **Исключения** задаются масками с `*` и `?`, без учёта регистра:
  - на уровне аккаунта маска сравнивается с именем репозитория (`test-*`);
  - на глобальном уровне — с полным именем `owner/repo` (`someone/*`).
  
  Исключённые репозитории не бэкапятся и не считаются новыми. Если репозиторий есть в списке и одновременно подпадает под исключение, исключение главнее, это пишется в лог как предупреждение.
- **FR-1.7.** Каждый репозиторий в настройках хранит **GitHub ID** (числовой, неизменный при переименовании). По нему распознаётся переименование (FR-2.5).
- **FR-1.8.** Если токена нет, программа работает анонимно: видны только публичные репозитории, лимит API — 60 запросов в час. Об анонимном режиме пишется предупреждение.

### 6.2. Обнаружение репозиториев

- **FR-2.1. Сбор доступных репозиториев.** Объединение (без дублей, по ID) результатов:
  - `GET /user/repos?affiliation=owner,collaborator,organization_member&visibility=all` — всё, что доступно токену;
  - для каждого аккаунта-организации — `GET /orgs/{org}/repos?type=all`;
  - для каждого аккаунта-пользователя — `GET /users/{login}/repos?type=all` (для чужого пользователя это только публичные репозитории; его приватные, где вы коллаборатор, придут из `/user/repos`).
- **FR-2.2. Новый репозиторий аккаунта.** Owner — отслеживаемый аккаунт, репозитория нет в его списке, он не исключён.
- **FR-2.3. Новый репозиторий вне аккаунтов.** Owner не входит в отслеживаемые аккаунты (например, вы коллаборатор у чужого пользователя), репозитория нет в группе отдельных репозиториев, он не исключён. Предлагается добавить его в группу отдельных репозиториев.
- **FR-2.4. Пропавший репозиторий.** Репозиторий есть в настройках, но не найден при сборе, и `GET /repos/{owner}/{repo}` вернул 404 или 403. Программа:
  - сообщает о нём;
  - выставляет в настройках `status: "Unavailable"`;
  - **ничего не удаляет**: клон, архивы и файл состояния остаются;
  - больше не пытается его бэкапить.
  
  Если репозиторий снова стал доступен, статус автоматически возвращается в `Active`, об этом пишется уведомление.
- **FR-2.5. Переименованный репозиторий.** Репозиторий с тем же ID найден под другим `owner/name` (переименование или перенос в другой аккаунт). Для **папки архивов** программа предлагает:
  - **а)** переименовать папку архивов и обновить имя в настройках;
  - **б)** обновить имя в настройках и продолжить работу в старой папке архивов (старый путь записывается в `path`).
  
  **Папка клона** в любом варианте переносится под новое имя (`<sourcesRoot>\<newOwner>\<newRepo>`) и получает новый URL remote. Если перенести не удалось, старый клон удаляется и выполняется повторное клонирование. Клон — это локальный кэш, архивы при этом не затрагиваются.
- **FR-2.6. Предложение для настроек.** Для каждого нового репозитория показываются:
  - URL, owner, видимость, признаки fork и archived, ветка по умолчанию, наличие wiki;
  - предлагаемая запись в настройки: имя, ID, ветка (`null` = по умолчанию), итоговая папка.
  
  Возможные действия:
  - **добавить** (с правкой ветки и пути);
  - **пропустить в этот раз** (спросит снова при следующем запуске);
  - **исключить** (имя добавляется в `exclude` аккаунта или глобальный).
- **FR-2.7.** Обнаружение выполняется в начале каждого запуска, кроме запуска с фильтром `--repo`. С фильтром `--account` обнаружение выполняется только для этого аккаунта.
- **FR-2.8.** Изменения в `backup-config.json` записываются атомарно (через временный файл), перед записью предыдущая версия сохраняется в `backup-config.json.bak`.

### 6.3. Структура каталогов

Клоны и архивы хранятся **в разных деревьях каталогов**. Архивы можно держать под облачной синхронизацией (OneDrive), а клоны остаются только на локальном диске.

**Архивы:**
- **FR-3.1.** Папка архивов репозитория по умолчанию: `<backupRoot>\<owner>\<repo>`. Правило одинаково для своих и для чужих репозиториев.
- **FR-3.2.** Если у аккаунта задан `path`, он **заменяет** `<backupRoot>\<owner>`, и папка архивов — `<account.path>\<repo>`.
- **FR-3.3.** Если у репозитория задан `path`, он **целиком заменяет** путь к папке архивов репозитория.

**Клоны:**
- **FR-3.4.** Корень клонов `sourcesRoot` по умолчанию — `sources\` в папке exe. В `backup-config.json` можно задать абсолютный путь к другой папке.
- **FR-3.5.** Клон репозитория: `<sourcesRoot>\<owner>\<repo>`, клон wiki: `<sourcesRoot>\<owner>\<repo>.wiki`. Переопределения `path` аккаунта и репозитория на клоны **не влияют**.

**Общие правила:**
- **FR-3.6.** Все пути в `backup-config.json` (`backupRoot`, `sourcesRoot`, `path`) только абсолютные. Относительный путь — ошибка валидации при старте.
- **FR-3.7.** Две записи с одной и той же итоговой папкой архивов — ошибка валидации при старте.
- **FR-3.8.** Если `sourcesRoot` находится внутри `backupRoot` или внутри папки архивов какого-либо репозитория, при старте выдаётся предупреждение: клоны попадут в облачную синхронизацию.
- **FR-3.9.** Раскладка на диске:

```
<sourcesRoot>\                         (по умолчанию <папка exe>\sources, только локальный диск)
├── .tmp\                              ← временные архивы до переноса (FR-7.4)
└── askrinnik\
    ├── my-repo\                       ← клон репозитория
    └── my-repo.wiki\                  ← клон wiki (если есть)

<backupRoot>\                          (например, внутри OneDrive)
└── askrinnik\
    └── my-repo\                       ← папка архивов репозитория
        ├── .backup-state.json                                    ← файл состояния
        ├── askrinnik_my-repo_20261002-143015_a1b2c3d4e5.zip      ← архивы репозитория
        └── askrinnik_my-repo.wiki_20261002-143020_9f8e7d6c5b.zip ← архивы wiki
```

### 6.4. Работа с git

- **FR-4.1.** Git вызывается как внешний процесс (`git.exe`). Путь берётся из `PATH`, если в настройках не задан явно.
- **FR-4.2. Первичное клонирование.** `git clone` в папку клона (FR-3.5) со всеми ветками и тегами, затем:
  - checkout нужной ветки;
  - инициализация сабмодулей (рекурсивно);
  - получение LFS-файлов **только для выбранной ветки**.
- **FR-4.3. Обновление.** Клон только для чтения, источником правды является сервер:
  1. `git fetch origin --prune --prune-tags --tags --force`;
  2. `git checkout -B <branch> origin/<branch>`;
  3. `git reset --hard origin/<branch>`;
  4. `git clean -ffdx`;
  5. `git submodule sync --recursive`;
  6. `git submodule update --init --recursive --force`;
  7. `git lfs pull`.
  
  Локальные изменения при этом теряются, это ожидаемое поведение.
- **FR-4.4. Выбор ветки.**
  - Если в настройках ветка не указана — ветка по умолчанию на GitHub.
  - Если указанной ветки на сервере нет — переключение на ветку по умолчанию, предупреждение в лог и в сводку (статус `Warning`).
- **FR-4.5.** Пустой репозиторий (без коммитов) обрабатывается как обычный, отдельный статус не нужен: клон создаётся, архив не создаётся, потому что архивировать нечего. Это фиксируется в логе.
- **FR-4.6.** Для git включается `core.longpaths=true`, чтобы работали длинные пути.
- **FR-4.7.** Весь вывод git (stdout и stderr) построчно пишется в лог (см. 6.10). Ошибка определяется **по коду возврата**, потому что git пишет обычный прогресс в stderr.

### 6.5. Wiki

- **FR-5.1.** Если у репозитория включена wiki (`has_wiki` в API), программа обрабатывает `https://github.com/<owner>/<repo>.wiki.git` в папку `<sourcesRoot>\<owner>\<repo>.wiki` по тем же правилам (FR-4.x, 6.6, 6.7), на ветке по умолчанию.
- **FR-5.2.** Wiki включена, но страниц нет, и git-репозиторий wiki не существует — это не ошибка. Wiki пропускается с отметкой в логе.
- **FR-5.3.** Архив wiki создаётся отдельно: `<owner>_<repo>.wiki_<yyyyMMdd-HHmmss>_<hash>.zip`. Он лежит в папке архивов репозитория.
- **FR-5.4.** В файле состояния у wiki отдельная секция, решение об архивации wiki принимается независимо от репозитория.

### 6.6. Определение изменений и файл состояния

- **FR-6.1. Файл состояния.** `.backup-state.json` в папке архивов репозитория (рядом с архивами, которые он описывает) хранит записи обо всех созданных архивах репозитория и wiki. Для каждого архива:
  - имя файла;
  - дата создания (местное время со смещением);
  - ветка checkout;
  - полный SHA HEAD;
  - размер;
  - снимок ссылок: все ветки `origin/*` и все теги → SHA.

```json
{
  "schemaVersion": 1,
  "repositoryId": 123456789,
  "fullName": "askrinnik/my-repo",
  "repository": {
    "archives": [
      {
        "file": "askrinnik_my-repo_20261002-143015_a1b2c3d4e5.zip",
        "createdAt": "2026-10-02T14:30:15+03:00",
        "branch": "main",
        "headCommit": "a1b2c3d4e5f60718293a4b5c6d7e8f9012345678",
        "sizeBytes": 10485760,
        "refs": {
          "heads/main": "a1b2c3d4e5f60718293a4b5c6d7e8f9012345678",
          "heads/dev": "77f0e1d2c3b4a5968778695a4b3c2d1e0f9a8b7c",
          "tags/v1.0": "c3d4e5f60718293a4b5c6d7e8f9012345678a1b2"
        }
      }
    ]
  },
  "wiki": { "archives": [] }
}
```

- **FR-6.2. Алгоритм решения** (отдельно для репозитория и для wiki):
  1. Клона нет (например, удалили папку `sources` или сменили `sourcesRoot`) → клонировать и сравнить снимок с последним архивом по пп. 2 и 4. Архив создаётся, только если есть изменения: само по себе повторное клонирование новый архив не создаёт.
  2. Берётся **последняя** запись об архиве. Если её файл **физически отсутствует** на диске, считается, что архива нет: обновить клон и архивировать. Файл-заглушка OneDrive («только в облаке») считается существующим, содержимое архива не читается.
  3. **Быстрая проверка:** `git ls-remote origin` (учитываются только `refs/heads/*` и `refs/tags/*`, без `refs/pull/*`). Если снимок совпадает со снимком последнего архива **и** ветка checkout та же → статус `UpToDate`, без fetch и без архива.
  4. Иначе — обновление клона (FR-4.3), затем снимок через `git for-each-ref`. Если он отличается от снимка последнего архива или изменилась ветка checkout → архивировать, иначе `UpToDate`.
- **FR-6.3.** Новый архив нужен при **любом** изменении: в выбранной ветке, в любой другой ветке, в тегах (добавление, удаление, перенос), а также при смене ветки checkout в настройках.
- **FR-6.4.** Запись в файл состояния добавляется **только после** успешного создания архива. Файл состояния пишется атомарно.

### 6.7. Архивация

- **FR-7.1.** Архив создаётся программой 7-Zip (`7z.exe`) в формате **ZIP**, без пароля. Путь по умолчанию `C:\Program Files\7-Zip\7z.exe`, его можно переопределить в настройках.
- **FR-7.2.** Архив содержит папку клона целиком, включая `.git`. Корневая папка внутри архива — `<repo>\` (для wiki — `<repo>.wiki\`), как папка клона на диске.
- **FR-7.3.** Имя архива:

  ```
  <owner>_<repo>_<yyyyMMdd-HHmmss>_<shortHash>.zip
  ```

  - `owner` и `repo` — как на GitHub;
  - время — местное время ОС на момент архивации;
  - `shortHash` — первые **10** символов SHA HEAD выбранной ветки.
  
  Имя ветки в имя архива не входит. Уникальность имени обеспечивает время, а решение об архивации принимает файл состояния (6.6).
- **FR-7.4.** Архив создаётся и проверяется **на локальном диске**, в `<sourcesRoot>\.tmp\`, а не в папке архивов. Так облачная синхронизация не подхватит недописанный файл. После успешной проверки архив переносится в папку архивов:
  - если папки на одном томе — переименованием;
  - если на разных — копированием во временное имя в папке назначения, затем переименованием и удалением исходника.
  
  Если создание, проверка или перенос не удались, временные файлы удаляются, запись в файл состояния не добавляется.
- **FR-7.5.** Перед переносом архив проверяется (`7z t`). Проверку можно отключить в настройках.
- **FR-7.6.** Архивы копятся бессрочно: программа их не удаляет.
- **FR-7.7.** Вывод 7-Zip пишется в лог так же, как вывод git.

### 6.8. История

- **FR-8.1.** История хранится в SQLite-базе `data\history.db` рядом с exe. Состояние архивов остаётся в `.backup-state.json`: оно главное для решения об архивации.
- **FR-8.2. История запусков.** Для каждого запуска:
  - начало и конец;
  - режим: `Interactive`, `Silent`, `Ui`, флаг `DryRun`;
  - фильтр (`--account` или `--repo`);
  - итоговый код возврата;
  - счётчики по статусам.
- **FR-8.3. Элементы запуска.** По каждому репозиторию и wiki в запуске:
  - статус;
  - длительность;
  - ветка;
  - HEAD;
  - имя созданного архива;
  - список изменившихся ссылок;
  - текст ошибки.
- **FR-8.4. События обнаружения.** Новые, пропавшие, переименованные и вернувшиеся репозитории с принятым решением: добавлен, пропущен, исключён, переименована папка, сохранена старая папка, а также кем принято решение (пользователь или автоматически в тихом режиме).
- **FR-8.5. История архивов репозитория** в UI строится из `.backup-state.json`: все архивы, дата, хеш, размер, изменившиеся ссылки, наличие файла на диске. При необходимости дополняется данными запусков.
- **FR-8.6.** Схема базы создаётся и обновляется автоматически при старте (миграции EF Core).
- **FR-8.7.** Просмотр истории только в UI. Очистка истории — позже, вместе с очисткой архивов.

### 6.9. Консольное приложение (`GitHubBackup.Cli.exe`)

- **FR-9.1. Команды:**

| Команда | Назначение |
|---|---|
| `backup` | Обнаружение и бэкап (основная команда) |
| `set-token` | Сохранить токен в Windows Credential Manager. Ввод скрыт, токен не передаётся аргументом |
| `validate` | Проверить настройки, наличие инструментов и токен, ничего не меняя |

- **FR-9.2. Параметры `backup`:**

| Параметр | Назначение |
|---|---|
| `--account <url\|login>` | Только репозитории одного аккаунта (обнаружение — только для него) |
| `--repo <url\|owner/name>` | Только один репозиторий (без обнаружения) |
| `--dry-run` | Показать, что было бы сделано, без изменений |
| `--silent` | Тихий режим: никаких вопросов, решения принимаются автоматически |
| `--config <path>` | Путь к `backup-config.json` (по умолчанию рядом с exe) |

  Плюс любые ключи конфигурации .NET (`--GitHub:Token=...` и т. п.). `--account` и `--repo` вместе не используются.
- **FR-9.3. Интерактивный режим** (по умолчанию). При обнаружении новых, пропавших и переименованных репозиториев программа задаёт вопросы в консоли (FR-2.6, FR-2.5) с возможностью править ветку и путь.
- **FR-9.4. Тихий режим** (`--silent`):
  - новые репозитории **автоматически добавляются** в настройки (ветка по умолчанию, путь по умолчанию) и бэкапятся;
  - пропавшие автоматически помечаются `Unavailable`;
  - переименованные — см. раздел 13, П-1;
  - код возврата `3`, если были такие события.
- **FR-9.5. Проверочный прогон** (`--dry-run`):
  - выполняется обнаружение и быстрая проверка (`ls-remote`);
  - показывается, что было бы сделано: клонирование, обновление, архив и его имя, новые и пропавшие репозитории;
  - ничего не клонируется, не обновляется, не архивируется, настройки и файлы состояния не меняются, вопросы не задаются.
- **FR-9.6.** Если консоль не интерактивна (ввод перенаправлен) и `--silent` не указан, программа завершается с ошибкой `2` и подсказкой использовать `--silent`.
- **FR-9.7. Сводка в конце** — таблица по репозиториям: статус, архив, длительность, ошибка. Затем итоги по статусам и путь к логу.
- **FR-9.8. Статусы элемента:**

| Статус | Значение |
|---|---|
| `Archived` | Создан новый архив |
| `UpToDate` | Изменений нет |
| `Warning` | Выполнено с предупреждением (например, откат на ветку по умолчанию) |
| `Failed` | Ошибка |
| `Skipped` | Пропущен (исключён, недоступен, не подтверждён) |
| `WouldArchive` | Только в dry-run: был бы создан архив |
| `WouldClone` | Только в dry-run: было бы выполнено клонирование |

- **FR-9.9.** Ошибка одного репозитория не прерывает запуск: остальные обрабатываются, ошибка попадает в сводку, лог и историю.
- **FR-9.10. Коды возврата** (при нескольких условиях действует первое подходящее сверху):

| Код | Значение |
|---|---|
| `2` | Критическая ошибка: настройки, инструменты, токен, блокировка, сбой API при обнаружении |
| `1` | Часть репозиториев завершилась с `Failed` |
| `3` | Ошибок нет, но были новые, пропавшие или переименованные репозитории |
| `0` | Всё успешно |

### 6.10. Логирование

- **FR-10.1.** В коде используется `ILogger<T>` (Microsoft.Extensions.Logging), провайдер — Serilog.
- **FR-10.2.** Логи пишутся в папку `logs\` рядом с exe, по файлу в день:
  - `logs\githubbackup-YYYYMMDD.log` — читаемый текст;
  - `logs\githubbackup-YYYYMMDD.json` — структурированный лог (CLEF, по строке JSON на событие).
  
  Файлы логов не удаляются автоматически (очистка — позже). Уровни настраиваются в `appsettings.json`.
- **FR-10.3.** В каждой записи есть контекст: ID запуска и, где применимо, репозиторий (`owner/repo`) и операция (`clone`, `fetch`, `archive`…).
- **FR-10.4. Вывод внешних процессов.**
  - Перед запуском — команда целиком, секреты замаскированы.
  - Каждая строка stdout и stderr — отдельная запись со свойствами `Tool`, `Stream`, `Repository`.
  - После завершения — код возврата и длительность.
- **FR-10.5. OpenTelemetry** (по умолчанию выключено, включается в `appsettings.json`):
  - трейсы: запуск → обнаружение → репозиторий → операции;
  - метрики: число репозиториев по статусам, длительности, размер архивов;
  - экспорт по OTLP на заданный адрес (например, .NET Aspire Dashboard или Seq).
- **FR-10.6.** Токен и заголовки авторизации никогда не пишутся в лог: в сообщениях, свойствах и тексте исключений они заменяются на `***`.

### 6.11. Аутентификация

- **FR-11.1. Токен ищется по цепочке**, первый найденный побеждает:
  1. Ключ `GitHub:Token` из `IConfiguration`. Любой стандартный источник: `appsettings.json`, переменная окружения `GitHubBackup__GitHub__Token`, user-secrets (в окружении Development), командная строка.
  2. Запись программы в **Windows Credential Manager** (Generic Credential, target `GitHubBackup:https://github.com`). Создаётся командой `set-token` или из UI.
  3. `gh auth token` (если GitHub CLI установлен и авторизован).
  4. Не найден — анонимный режим (FR-1.8).
  
  Какой источник использован, пишется в лог, значение — нет.
- **FR-11.2.** `git credential fill` (Git Credential Manager) **не используется**: он может открыть окно входа и подвесить тихий режим.
- **FR-11.3. Токен для git.** Тот же токен передаётся процессу git **через переменные окружения** (`GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_n`, `GIT_CONFIG_VALUE_n` с `http.https://github.com/.extraHeader`). Токен не попадает:
  - в аргументы командной строки;
  - в URL remote;
  - в `.git/config`, а значит и в архивы.
  
  Для git-процессов отключаются интерактивные запросы учётных данных (`GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`).
- **FR-11.4. Рекомендуемый токен:** classic PAT со scope `repo` и `read:org`. В README объясняется, почему fine-grained PAT может не дать доступ к репозиториям организаций и к чужим репозиториям, где вы коллаборатор.
- **FR-11.5. GitHub API.** Используется Octokit.NET за собственной абстракцией. Адрес API настраивается (по умолчанию `https://api.github.com`). Остаток лимита запросов пишется в лог. Если лимит исчерпан во время обнаружения, это критическая ошибка с указанием времени сброса лимита.

### 6.12. UI-приложение (`GitHubBackup.exe`, WPF + MVVM)

- **FR-12.1. Главное окно.**
  - Дерево «аккаунты → репозитории» и группа отдельных репозиториев, у каждого статус и дата последнего архива.
  - Кнопки: «Бэкап всего», «Бэкап аккаунта», «Бэкап репозитория», переключатель «Dry run».

- **FR-12.3. Прогресс.** Текущий репозиторий и операция, живая лента лога, кнопка отмены. Отмена корректно завершает текущую операцию, временные файлы удаляются.

- **FR-12.5. Редактор настроек.**

## 7. Конфигурация

Оба exe лежат в одной папке и используют общие файлы.

### 7.1. Раскладка папки приложения

```
<папка приложения>\
├── GitHubBackup.exe          ← UI
├── GitHubBackup.Cli.exe      ← консоль
├── appsettings.json          ← настройки приложения (только чтение)
├── backup-config.json        ← что и куда бэкапить (программа читает и пишет)
├── backup-config.json.bak
├── logs\
├── data\history.db
└── sources\                  ← клоны (по умолчанию, см. FR-3.4)
```

Папка приложения должна быть доступна на запись (например, не `C:\Program Files`), если `sourcesRoot` не переопределён.

### 7.2. `appsettings.json` (через `IConfiguration`, `IOptions<T>` с валидацией при старте)

```json
{
  "GitHub": {
    "ApiBaseUrl": "https://api.github.com",
    "Token": null
  },
  "Tools": {
    "GitPath": null,
    "SevenZipPath": "C:\\Program Files\\7-Zip\\7z.exe"
  },
  "Backup": {
    "ConfigPath": "backup-config.json",
    "ShortHashLength": 10,
    "VerifyArchive": true
  },
  "History": {
    "DatabasePath": "data\\history.db"
  },
  "OpenTelemetry": {
    "Enabled": false,
    "OtlpEndpoint": "http://localhost:4317"
  },
  "Serilog": {
    "MinimumLevel": { "Default": "Information" }
  }
}
```

**Источники конфигурации** (по возрастанию приоритета, более поздний переопределяет более ранний):

1. `appsettings.json` рядом с exe. Файл обязателен: без него запуск завершается ошибкой конфигурации.
2. user-secrets — только в окружении `Development`.
3. Переменные окружения с префиксом `GitHubBackup__`, например `GitHubBackup__Backup__ShortHashLength`. Переменные без префикса и файлы `appsettings.{Environment}.json` не читаются.
4. Командная строка, `--Section:Key=value`.

Окружение задаёт переменная `DOTNET_ENVIRONMENT`, по умолчанию `Production`.

**Проверка при старте.** Ошибка любого правила завершает запуск с кодом `2` (FR-9.10); в stderr выводится по строке на ошибку с именем ключа, без стека и без значения `GitHub:Token`:

- `GitHub:ApiBaseUrl` — абсолютный URI со схемой `http` или `https`;
- `Tools:GitPath`, `Tools:SevenZipPath` — абсолютные пути, если заданы (наличие файла проверяет `IToolLocator`);
- `Backup:ConfigPath`, `History:DatabasePath` — не пустые;
- `Backup:ShortHashLength` — от 4 до 40;
- `OpenTelemetry:OtlpEndpoint` — абсолютный URI, если `OpenTelemetry:Enabled` равно `true`;
- `Serilog:MinimumLevel:Default` и каждое значение `Serilog:MinimumLevel:Override:<SourceContext>` — одно из `Verbose`, `Debug`, `Information`, `Warning`, `Error`, `Fatal`.

`Serilog:MinimumLevel:Override` необязателен: он задаёт уровень для источников с указанным префиксом (например, `"Microsoft": "Warning"`).

`GitPath: null` — git берётся из `PATH`. Пути внутри `appsettings.json` (`ConfigPath`, `DatabasePath`, логи) отсчитываются от папки exe. Это не противоречит FR-3.4: правило про абсолютные пути касается путей бэкапа в `backup-config.json`.

### 7.3. `backup-config.json` (собственный сервис чтения и записи)

```json
{
  "schemaVersion": 1,
  "backupRoot": "C:\\Users\\Sanya\\OneDrive\\GitHubBackups",
  "sourcesRoot": null,
  "exclude": [ "someone/*" ],
  "accounts": [
    {
      "url": "https://github.com/askrinnik",
      "path": null,
      "exclude": [ "test-*" ],
      "repositories": [
        { "name": "my-repo", "id": 123456789, "branch": null, "path": null, "status": "Active" },
        { "name": "old-tool", "id": 223456789, "branch": "legacy", "path": "E:\\Archive\\old-tool", "status": "Active" }
      ]
    },
    { "url": "https://github.com/AMTOSS", "path": "E:\\WorkBackups\\AMTOSS", "exclude": [], "repositories": [] },
    { "url": "https://github.com/get-the-manual", "path": null, "exclude": [], "repositories": [] }
  ],
  "repositories": [
    { "url": "https://github.com/someone-else/library", "id": 323456789, "branch": "develop", "path": null, "status": "Active" }
  ]
}
```

- `status` принимает значения `Active` и `Unavailable`.
- `sourcesRoot: null` означает `<папка exe>\sources`.
- `path` аккаунта и репозитория задают только папку **архивов** (FR-3.2, FR-3.3).
- Валидация при загрузке:
  - `backupRoot` задан и абсолютный; `sourcesRoot`, если задан, абсолютный;
  - предупреждение, если клоны оказываются внутри дерева архивов (FR-3.8);
  - все `path` абсолютные;
  - URL корректные и указывают на github.com;
  - нет дублей репозиториев (по ID и по имени);
  - нет совпадающих итоговых папок.

### 8.2. Основные компоненты

| Компонент | Ответственность |

### 8.4. Совместная работа CLI и UI

- **NFR-SYS-1.** Одновременно может выполняться только один запуск бэкапа (именованный mutex на уровне ОС). Второй запуск завершается с кодом `2` и сообщением «бэкап уже выполняется».
- **NFR-SYS-2.** UI перечитывает `backup-config.json` перед каждым запуском и после закрытия редактора настроек.

## 9. Порядок выполнения запуска

1. Загрузка и валидация `appsettings.json` и `backup-config.json`.
2. Проверка инструментов (git, git-lfs, 7z).
3. Получение токена (FR-11.1).
4. Захват блокировки запуска (NFR-SYS-1).
5. Обнаружение (если нет `--repo`).
6. Принятие решений обнаружения стратегией текущего режима, сохранение `backup-config.json` (кроме dry-run).
7. Формирование списка работ: активные, не исключённые, подходящие под фильтр.
8. Последовательная обработка каждого элемента (репозиторий, затем его wiki): определение изменений → обновление → архивация → запись состояния.
9. Запись истории, вывод сводки, код возврата.

## 10. Нефункциональные требования

| ID | Требование |
|---|---|
| NFR-1 | **Безопасность.** Токен не попадает в логи, аргументы процессов, `.git/config` и архивы (FR-10.6, FR-11.3) |
| NFR-2 | **Надёжность.** Атомарная запись архивов, `backup-config.json` и `.backup-state.json`. Сбой посреди операции не оставляет «полузаписанных» файлов под окончательными именами |
| NFR-3 | **Изоляция ошибок.** Ошибка одного репозитория не прерывает запуск (FR-9.9) |
| NFR-4 | **Отмена.** Ctrl+C в CLI и кнопка в UI корректно останавливают текущий процесс git или 7z, временные файлы удаляются |
| NFR-5 | **Эффективность.** Неизменённые репозитории проверяются без fetch (быстрая проверка через `ls-remote`) |
| NFR-6 | **Сопровождаемость.** DI везде, зависимости через интерфейсы, `TreatWarningsAsErrors`, nullable reference types, анализаторы .NET |
| NFR-7 | **Язык.** Код, комментарии, логи, сообщения CLI и UI — на английском. Заголовки issues, коммиты, pull request и комментарии к issues и PR — на английском. Документация и тексты issues — на русском |
| NFR-8 | **Развёртывание.** Framework-dependent (.NET 10 установлен), публикация в одну папку, single-file exe |

## 13. Предложения по умолчанию, требующие подтверждения

Решения, которые не обсуждались явно. Я выбрал вариант по умолчанию, при ревью их нужно подтвердить или изменить.

| № | Вопрос | Предложение |
|---|---|---|
| П-1 | Что делать с **переименованным** репозиторием в тихом режиме | Вариант «б» из FR-2.5: обновить имя в настройках, продолжить в старой папке. Файлы не переносятся, это безопаснее |
| П-2 | Планировщик заданий | В фазе 5 только инструкция в README. Команду регистрации задачи не делаем |
| П-4 | Проверка архива `7z t` после создания | Включена по умолчанию (`VerifyArchive: true`) |
| П-5 | Записывать ли dry-run в историю | Да, с флагом `DryRun` |
| П-6 | Где хранится `backupRoot` | В `backup-config.json` (вместе с остальными настройками бэкапа, его правит UI) |
| П-7 | Неинтерактивная консоль без `--silent` | Ошибка `2` с подсказкой (FR-9.6) |
| П-8 | `refs/pull/*` и прочие служебные ссылки GitHub | Не учитываются, только ветки и теги |
| П-9 | Срок хранения файлов логов | Без автоудаления (очистка — позже) |
| П-10 | Свой путь к клонам для отдельного аккаунта или репозитория | Не нужен: только общий `sourcesRoot` (FR-3.5) |

| П-13 | Клон пропал (удалили `sources`), а на сервере изменений нет | Клонировать заново, новый архив не создавать (FR-6.2, п. 1) |
